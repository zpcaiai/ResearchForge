# Batch 04-pre — 20 篇论文复现研究协议 v1.0

**目的：** 在写任何 runtime 代码之前，测出 ResearchForge 目标域内论文的**真实复现率分布**。
这个分布决定 `source-result-reproducer` 的分级门槛、`reproduction-fallback-planner` 的降级路径是否够用，以及整个执行平面是否值得建。

**预计工时：** 1 名工程师 2 周（agent 臂 20 篇 × 4h 时间盒 + 人工臂 8 篇 × 8h 上限 + 分析）
**产出：** `repro_study_tracker.xlsx`、RL 分布、失败码分布、agent-vs-human 差距、以及一个二元 go/no-go 决策

---

## 0. 这个研究要回答的三个问题

1. **P(RL≥3)** —— 有多大比例的论文能把主结果在容差内复现？这决定 `CM_MEASURED`（最强的产品形态）覆盖多少项目。
2. **P(RL≥1)** —— 有多大比例的论文代码根本能跑起来？这决定整个执行平面（沙箱、实验树搜索、代码脚手架）是否有意义。**如果连 RL1 都罕见，ResearchForge 的重心就不在实验上。**
3. **agent 与人的差距有多大** —— 同一批论文，agent 达到的 RL 与熟练人类达到的 RL 之差。这是唯一能指导「该往哪投工程」的数字。

第 3 个问题最容易被忽略，但它最重要：如果人能到 RL3 而 agent 只能到 RL1，问题在 agent 的工程能力，可以修；如果人和 agent 都只能到 RL1，问题在论文本身，修不了，只能靠降级路径。

## 1. 先验：不要凭空定阈值

已有文献给了我们校准点：

| 来源 | 条件 | 结果 |
|---|---|---|
| Collberg & Proebsting (2016)，计算机系统 | **限时、不联系作者** | 代码可重跑 **32.3%** |
| 同上 | 充裕时间、作者不可联系 | 48.3% |
| 同上 | 充裕时间、作者可联系 | 54.0% |
| Raff (2019)，255 篇 ML 论文 | 独立复现（从论文出发，非从代码） | 63.5% |
| Baker (2016)，Nature 调查 | 跨学科自我报告 | >70% 研究者曾复现他人实验失败 |
| Pham et al. (2020) | 16 次相同的 LeNet5 训练 | 准确率跨度 8.6%–99.0% |

**第一行就是我们的处境**：时间盒内、不联系作者、只有公开产物 —— 先验期望 **P(代码可跑) ≈ 32%**。

这有两个后果：

- 我在评审里给的「低于 30% 就停」是**错的门槛**。32% 差不多就是这个领域的常态，而不是灾难信号。真正的问题不是"率够不够高"，而是"降级路径在这个率下是否成立"。下面第 6 节重新给了决策规则。
- Pham et al. 的结果意味着**容差不能拍脑袋定 ±5%**。对训练过程随机性大的任务，必须先测同种子/跨种子的自身方差，再定容差 —— 否则你会把噪声判成复现失败。这一步写在 §4 步骤 0。

## 2. 抽样框：**不要手工挑这 20 篇**

这是整个协议里最容易做错、也最致命的一步。

手工挑选会不可避免地偏向"我听说过的、维护得好的、明星实验室的"仓库，把复现率系统性抬高。用这样的 20 篇算出 60% 的成功率，然后按 60% 去设计门槛，上线后遇到真实分布会全线崩溃。

**规则：定义抽样框，然后随机抽。抽到什么做什么，包括看起来注定失败的那些。**

### 2.1 框的定义（v1 域，与 ARCHITECTURE 的域限定一致）

一篇论文进入抽样框，当且仅当它同时满足：

- 发表于**单一指定会议的单一年份**（建议 ICLR 2025 或 NeurIPS 2024 的 accepted papers，通过 OpenReview API 可完整枚举，避免"我记得的那些"）；
- 论文或 OpenReview 页面中含**指向代码仓库的链接**（无代码链接的直接记为 RL0/`NO_CODE`，但仍应按比例进入样本 —— 见 2.3）；
- 主实验声称可在**单卡 ≤24GB、单次实验 <1 GPU-hour** 的设置下运行，或论文提供了这样的缩小设置；
- 使用**公开可下载的 benchmark**，无需申请或签署协议。

后两条按论文声明筛，不按实际能力筛 —— 实际能力正是我们要测的。

### 2.2 抽样程序

```bash
python tools/sample_frame.py --frame frame.csv --n 20 --seed 20260811 --out sample.csv
```

抽样种子写死并记录。**样本一旦抽出即冻结**，不得因为"这篇看起来太难"而替换。任何替换都必须记录理由并单独统计 —— 替换本身就是数据。

### 2.3 分层

按两个维度分层，各层内随机抽，保证极端情况不被抽丢：

| 维度 | 层 | 目标配额 |
|---|---|---|
| 代码可得性 | 有官方仓库 / 仅第三方复现 / 无代码 | 14 / 3 / 3 |
| 计算量 | 可在 <10 GPU-min 完成主实验 / 10–60 GPU-min | 10 / 10 |

3 篇"无代码"看起来是浪费，其实不是：它们校准了 RL0 分支，而 RL0 分支的降级路径正是这次改动新增的核心机制，必须有真实样本验证。

## 3. 两个臂

| 臂 | 执行者 | 时间盒 | 是否可联系作者 | n |
|---|---|---|---|---|
| **A — agent** | 编码 agent（Codex/Claude Code），无人工干预 | 每篇 **4 小时** wall-clock | 否 | 20 |
| **B — 人类天花板** | 熟练 ML 工程师 | 每篇 **8 小时** | 否（保持可比） | 8（A 臂的随机子集） |

两臂**盲于彼此的结果**：B 臂执行者不得先看 A 臂的日志，否则测的是"人修 agent 的坑"而不是人的天花板。

B 臂只做 8 篇是成本妥协。它给出的是天花板的粗估，不是精确值 —— 报告时必须这么说。

---

## 4. 单篇执行步骤

**步骤 0（每篇必做，先于任何比对）—— 测自身方差。**
在能跑起来的前提下，用**不同随机种子**重复主实验 3 次，记录指标的标准差。容差取 `max(论文报告的方差, 本地实测 3 种子标准差 × 2, 相对 2%)`。跳过这一步而直接用固定 ±5%，在高方差任务上得到的"复现失败"是无意义的。

随后按分级逐层尝试，任一层达成即记录，时间盒用尽即停：

| 层 | 判据 | 注意 |
|---|---|---|
| **RL0** | 未复现 | 含无代码、依赖装不上、数据拿不到 |
| **RL1** | 环境可构建，入口脚本在缩小样本上**无错跑完** | 「没报错」只是 RL1，不是成功 |
| **RL2** | 缩小设置下指标的**方向与量级**与论文一致 | 缩小设置**永远不能**支撑 RL3/RL4 |
| **RL3** | **至少一个主结果**在步骤 0 定的容差内复现 | 必须是从论文里带 locator 读出的数值 |
| **RL4** | 主表**多数条目**在容差内复现 | — |

**每一条比对都必须成对记录**：`(claim_id, 论文报告值, 本地实测值, 容差, 判定, run_id, 论文中的位置)`。没有配对的测量不算证据。

失败原因只能从固定词表里选（与 `ReproductionLevel.schema.json` 一致），不接受自由文本：

`NO_CODE` · `DEPENDENCY_UNRESOLVABLE` · `HARDWARE_UNAVAILABLE` · `DATA_UNAVAILABLE` · `DATA_ACCESS_GATED` · `CHECKPOINT_MISSING` · `UNDOCUMENTED_PREPROCESSING` · `CONFIG_AMBIGUOUS` · `NONDETERMINISM` · `METRIC_DEFINITION_MISMATCH` · `NUMBERS_DIVERGE` · `TIMEBOX_EXCEEDED` · `LICENSE_BLOCKED`

一篇可以有多个失败码。**失败码分布比成功率更有工程价值** —— 它直接告诉你该建什么：如果 40% 是 `DEPENDENCY_UNRESOLVABLE`，该建的是依赖求解与镜像缓存；如果 40% 是 `UNDOCUMENTED_PREPROCESSING`，再好的沙箱也救不了，该建的是与作者/社区的信息通道。

---

## 5. 必须记录的字段

除 RL 与失败码外，每篇记录：

- **到达该 RL 的耗时**（分钟）。这是成本模型的唯一真实输入，比成功率更影响产品可行性。
- **时间盒是否用尽**（若是，RL 是下界而非真值）。
- **卡住的那一步**（自由文本，一句话）—— 用于事后聚类，但不替代失败码。
- **环境摘要**（镜像 digest、CUDA、driver）。
- **仓库最后提交日期、star 数、是否有 README 复现章节、是否提供 requirements 锁文件**。这些是廉价的**先验特征**，如果它们能预测 RL，`baseline-repo-finder` 就能在花 4 小时之前先排序，把时间盒花在更可能成功的仓库上。这是这次研究最可能产生的直接工程收益。

## 6. 决策规则（在看到数据之前写死）

事后调整阈值等于没有阈值。以下规则在开跑前冻结：

| 条件 | 结论 |
|---|---|
| **P(RL≥3) ≥ 0.30** | 按现设计推进。`CM_MEASURED` 是主路径，降级路径是兜底。 |
| **0.15 ≤ P(RL≥3) < 0.30** | 推进，但**把 `CM_REPORTED`/RL1 当作设计中心而非例外**。UI、文案、论文披露模板都要按"多数项目无法本地复现 baseline"来设计。 |
| **P(RL≥3) < 0.15 且 P(RL≥1) ≥ 0.40** | 执行平面仍有价值（代码能跑，可做相对比较与消融），但**放弃"超越论文报告数值"作为主要卖点**，重心转向诊断/评测/系统化类贡献。 |
| **P(RL≥1) < 0.40** | **停止建执行平面。** ResearchForge 重新定位为文献-创新-写作系统，实验执行降级为可选后端。这不是失败，是省下 6 个人月。 |
| **人类臂 RL 中位数 − agent 臂 RL 中位数 ≥ 2 级** | 差距在 agent 工程能力而非论文，优先投入依赖求解/环境修复/日志诊断，而不是急着改架构。 |

## 7. 统计诚实性（n=20 意味着什么）

n=20、真实 p≈0.33 时，95% 置信区间约为 **±21 个百分点**（Wilson 区间大致 0.16–0.55）。

**这意味着 n=20 能区分「大约三分之一」和「几乎为零」或「几乎全部」，但区分不了 30% 和 45%。**

因此：

- 上面的决策规则刻意设计成**粗粒度的分档**，而不是精确阈值 —— 因为 n=20 只支持粗粒度结论。
- 若某次结果恰好落在两档边界附近（例如 P(RL≥3) 落在 0.28–0.32），**不要照着分档硬判**，应追加 20 篇再决策。区分 30% 与 45% 需要约 n=60。
- 报告必须给出区间，不能只给点估计。用 Wilson 区间，不用正态近似（小样本比例下正态近似在边缘处失效）。

## 8. 这项研究本身的产出如何进入系统

- RL 分布 → `source-result-reproducer` 的默认时间盒与分层顺序
- 容差实测 → 取代 `±5%` 的硬编码默认值
- 失败码分布 → Batch 04 的工程优先级排序
- 先验特征与 RL 的相关性 → `baseline-repo-finder` 的排序函数
- 人类-agent 差距 → 决定投工程还是投降级路径
- **20 篇的完整记录本身就是 `retro_benchmark` 的第一批 fixture**，其中的 RL0/RL1/RL3 各挑一篇，正好构成 Batch 13 要求的三个 E2E fixture
