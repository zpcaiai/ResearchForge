**执行日期：** 2026-08-11

## 0. 先说结论

**这项研究这次真的跑了**，20 篇全部实测。但**冻结的决策规则并未被触发，它仍处于未评估状态**——因为本次探测的仪器本身是一个大的混淆因子。

看起来像是触发了：P(依赖可解析) = 3/20 = 15%，95% CI 上端 36%，低于 40% 的阈值。把它当成决定性结果是很有诱惑力的，而那恰恰是这项研究本身要防止的错误。

**站得住的结论只有一条，但它是干净的：**

> **40%（8/20）的样本因产物自身原因根本无法开始复现** —— 20% 没有公开代码，另外 20% 有代码但全树搜索后没有任何依赖声明。
> 这个数字**与我的环境完全无关**。由此 P(RL≥1) 的硬上界是 **60%，CI [39%, 78%]**。

60% 不低于 40%，**所以执行平面没有被这批数据判死刑**。

## 1. 抽样框：怎么在两条路都断了之后找到第三条

上一轮的结论是"做不了"，因为论文优先框（OpenReview）和仓库优先框（GitHub 搜索）都被封。这次重测发现了第三条路。

实测出网边界：

| 目标 | 容器直连 | WebFetch 通道 |
|---|---|---|
| `git clone` github.com | ✅ | — |
| PyPI | ✅ | — |
| `api.github.com/rate_limit` | ✅ | — |
| `api.github.com/search/*` | ❌ 403（策略封禁） | — |
| OpenReview / OpenAlex / arXiv / Crossref | ❌ 403 | ❌ 403 |
| **huggingface.co/api/daily_papers** | ❌ 403 | **✅ 通** |
| proceedings.neurips.cc | ❌ 403 | ✅ 通 |

**HF Daily Papers API 通过 WebFetch 可达，而且每条记录带 `arxiv id`、`title`、`githubRepo`、`githubStars`。**

关键是它**按日期机械枚举**——不需要我选查询词、不需要我判断哪篇值得进框。规则写死在 `FRAME_RULE.md`：2025-10-07 到 2025-12-30，每 7 天取一天，共 13 天，每天**取回全部条目**。得到 188 篇去重后的候选池，其中 144 篇有仓库、44 篇没有。

**没有仓库的那 44 篇恰好恢复了协议里的「无代码」层**——上一轮的 GitHub 搜索方案做不到这点，因为无代码的论文根本进不了那个框。协议原本给这一层分配 3/20 的配额，本次随机抽到 4/20。

## 2. 我在自己的仪器上发现了一个缺陷，并且修了

第一遍探测只在**仓库根目录**找依赖文件。7 个仓库因此被判为 `CONFIG_AMBIGUOUS`（无依赖声明）。

这个判定如果错了，那报出去的就是我的仪器误差，而不是关于世界的发现。所以我重新克隆这 7 个仓库，**全树搜索**：

- **3/7 确实在子目录有依赖文件**（`DCMoE/requirements.txt`、`Lumos-Nexus/requirements.txt`、`python/pyproject.toml`）——我的仪器确实不完整
- **但这 3 个即使找到了也全部解析失败**（两个卡在 PyTorch 固定版本，一个要求不同的 Python 版本）
- 4/7 是真的全树都没有任何依赖声明

修正后的分类：`CONFIG_AMBIGUOUS` 从 7 降到 4，`DEPENDENCY_UNRESOLVABLE` 从 6 升到 9。

**结论不变。仪器缺陷存在、被发现、被修正，而且修正后结论更强而不是更弱。**

## 3. 结果

### 3.1 与仪器无关的部分（这些数字可以直接用）

| | | |
|---|---|---|
| 论文没有公开仓库 | 4/20 = **20%** | CI [8%, 42%] |
| 仓库存在但全树无依赖声明 | 4/20 = **20%** | CI [8%, 42%] |
| ——占已克隆仓库的比例 | 4/16 = **25%** | CI [10%, 49%] |
| **因产物自身原因无法开始复现** | 8/20 = **40%** | CI [22%, 61%] |
| **→ P(RL≥1) 的硬上界** | **60%** | CI [39%, 78%] |

我装什么、装不装得上，都改变不了"这个仓库根本没发代码"或"这个仓库没有任何环境声明"。

### 3.2 被我的环境混淆的部分（不要当成仓库的属性）

依赖解析失败 9/20 = 45%。捕获到错误信息的 12 次失败中：

| 失败原因 | 次数 |
|---|---|
| **PyTorch/CUDA 固定版本轮子不在 PyPI 上** | **5** |
| 包名根本找不到 | 2 |
| Python 版本不兼容 | 2 |

前一类几乎肯定是我的环境造成的：这个容器**没有 conda、没有 `download.pytorch.org`、Python 固定在 3.11**。一个装备正常的研究者会解析掉其中一部分。

**所以这个 45% 是低估，不是高估。**

### 3.3 为什么决策规则不算被触发

两个方向相反、量级未知的偏差同时存在：

1. **HF Daily Papers 是策展的** → 偏向可见度高的工作 → 抬高复现率（乐观方向）
2. **探测环境缺 conda / PyTorch 索引 / 多版本 Python** → 压低复现率（悲观方向）

**一个夹在两个未受控偏差之间的点估计，不是对世界的测量。** 15% 这个数字既不能拿来触发规则，也不能拿来否定规则。

协议 §6 说决策规则冻结后不得事后调整——那是对的。但规则的前提是测量本身有效。仪器构成主要混淆项时，规则不该被判定为"触发"。**它仍然处于未评估状态。**

## 4. 这次研究真正的产出：工程优先级

我上一轮说过，研究的剩余价值在于"失败码分布决定先加固哪一块"。这个问题**得到了答案**，而且这部分结论对仪器偏差是稳健的——因为它问的是"失败的形状"，不是"失败的比例"。

| 失败码 | 占比 | 工程含义 |
|---|---|---|
| `DEPENDENCY_UNRESOLVABLE` | 45% | **可工程化，且是第一优先级** |
| `CONFIG_AMBIGUOUS` | 20% | 工程无解——仓库没有环境声明，只能靠信息通道 |
| `NO_CODE` | 20% | 工程无解——只能靠降级路径（这正是 `CM_NONE` 存在的理由） |
| `HARDWARE_UNAVAILABLE` | 10% | 可工程化：租算力 / 自动降级到缩小设置 |
| `DATA_UNAVAILABLE` | 5% | 部分可工程化：镜像源 |

### 应该先建什么

**依赖时间机器。** 失败原因里 PyTorch 固定版本占了压倒性多数。`result-reproducer` 需要的不是更好的沙箱，而是：

1. **历史 wheel 索引快照** —— 按仓库最后提交日期解析当时可得的包版本，而不是今天的 PyPI
2. **多 Python 版本解释器池** —— 3.9/3.10/3.11/3.12，按仓库声明选
3. **conda/mamba 后端** —— 20% 的仓库只提供 conda 规格
4. **PyTorch 专用索引** —— `download.pytorch.org`，CUDA 变体轮子不在 PyPI

这四条加起来直接打击 45% 的失败面，而且都不需要 GPU。**这是当前投入产出比最高的一块，而且在这次研究之前无法确定。**

反过来，`NO_CODE` + `CONFIG_AMBIGUOUS` 合计 40% 是工程救不了的。这 40% 只能靠 `reproduction-fallback-planner` 的降级路径——**这次研究间接确认了那条路径不是可选项，而是四成项目的唯一出路。**

---

## 5. 要得到可用的判定，还需要什么

在一台具备以下条件的机器上重跑 `probe.py`：

- conda/mamba + `download.pytorch.org` 索引 + 多版本 Python 解释器池
- 至少一块 GPU 与数据集下载通道（否则 RL2+ 永远测不到）
- 每篇 4 小时时间盒（本次实际中位耗时 **2.7 秒**，因为绝大多数在依赖解析阶段就停了）

并且必须先做**协议 §4 步骤 0**：同一实验换 3 个种子测自身方差再定容差。本次一次实验都没跑起来，所以步骤 0 无从做起。

样本可以直接复用——`sample.json` 里的 20 篇已冻结，种子 20260811 可完整复现。
